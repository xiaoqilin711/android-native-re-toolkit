# 案例研究：逆向一个 OLLVM + 自定义 VM 双重保护的 native 签名模块

[English](case-study.md) | [中文](case-study.zh-CN.md)

> **脱敏说明。** 本文刻意匿名：不出现厂商名、包名、真实偏移、密钥或样本值。目标是某大型电商 App 的 native 签名库（单个 ARM64 `.so`）。文中所有地址均为示意，非真实值。

## 我们面对的是什么

App 在 native 层计算请求签名，背后的库具备以下特征：

1. **符号已剥离** —— 只导出 `JNI_OnLoad`，其余函数全部通过 `RegisterNatives` 动态注册。
2. **OLLVM 混淆** —— 伪造控制流、跳转 thunk、平坦化的主分发器。
3. **自定义 VM 保护** —— 真正的哈希变换跑在一个 85 条指令的栈机字节码里，末尾再加一层"后处理"，让结果与任何标准哈希都对不上。
4. **反调试防护** —— seccomp + `TracerPid` + 反 Frida 字符串。

目标是在给定设备级根密钥的前提下，离线复现该签名。本文讲的是**方法**——工具层面的教训沉淀成了 `natool`。

## 第一回合 —— 识别 OLLVM（以及 IDA 为什么骗了我们）

最先跳出来的，是几乎每个基本块开头都重复出现的一对指令：

```asm
str wzr, [x20, #0x154]
str wzr, [x21, #0x150]
```

向一个没人读的固定栈偏移写入零。这就是 OLLVM 的**伪造控制流（BCF）**——只用死存储来制造死分支，让反编译器淹死在 `if (v20 == 0x154)` 的噪声里。

第二个特征是**跳转 thunk**。几乎每个函数的"入口"都是一个蹦床：

```asm
; 函数"入口"
;   保存 x0-x2
;   adrp + add  -> 真实函数体地址
;   br x9       -> 间接跳转到真实函数体
```

间接跳转 `br x9` 击穿了 IDA 的函数边界识别：函数被错误切分、错误合并，交叉引用消失。

### 我们必须内化的三个后果

1. **函数边界不可靠。** `bl` 边扫描和交叉引用会被 thunk 截断。
2. **调用者分析会漏。** 我们最初从一次 `bl` 扫描得出"Hmac-SHA1 没有调用者 → 死代码"的结论。**错。** 在 OLLVM 下，每个哈希入口都是 `br x9` thunk，调用是间接的，所以 `bl` 扫描**必然**漏掉它们。"没有直接调用者" ≠ "死代码"。
3. **纯静态阅读是死路。** F5 输出是垃圾。结论必须来自动态验证。

> **教训 1：在 OLLVM 下，"谁调用谁"不等于"谁参与算法"。** 签名路径上被调用的函数，可能是签名前的环境检查，而不是签名步骤。唯一可靠的办法是动态观察它的输入输出，而不是去读谁调用了它。

## 第二回合 —— 四步绕过法

**第一步：用 capstone 做全量线性扫描，一次一个 4 字节槽位。**

ARM64 是定长指令，所以线性扫描是安全的。陷阱在于 capstone 的一次性 `disasm` 会在遇到第一条非法字节时停止；每次反汇编 4 个字节就能避开这个提前停止。我们的第一次扫描报告了 719 条 `bl`；修正后的全量扫描找到了 **6971 条**——接近 10 倍。所有基于 719 条的"调用者分析"，都是在残缺的图上做的。

**第二步：枚举方法表，而不是猜入口。**

每个哈希都带一张*方法表*：`.data` 里的 `{函数指针0, 函数指针1} + IV + 轮常数`。扫描相邻两个都指向 `.text` 的 qword，能立刻浮出 SHA-256 表。有一个候选后来证明是反检测模块而非哈希——它尾随的数据解密出来是环境字符串（`.build.version.sdk`），且扫描对该表的引用为零。

**第三步：解开跳转 thunk。**

表里的函数指针本身也是 thunk。手工跟 `br x9` 得到真实函数体：

```
ptr_a -> 0x...:  cbz x0, ret  /  b 0x...     （一个哈希入口）
ptr_b -> 0x...:  b 0x...                     （另一个）
```

**第四步：静态定位，动态定论。**

静态分析给你的是*方法表、入口、一个好的 hook 偏移*，它给不了你算法。其余部分靠动态 hook + 受控差分测试。

## 第三回合 —— "SHA-1 不存在"（整个项目最漂亮的陷阱）

为了确认签名路径到底用了哪些哈希，我们在运行时扫描 `.so` 里的已知 IV 和轮常数。结果：

```
MD5_IV     -> 命中 1 次   （阳性对照）
SHA256_IV  -> 命中 1 次   （阳性对照）
SHA1_IV    -> 命中 0 次
SHA1_K     -> 命中 0 次
```

对 AES/ChaCha20/Salsa20/Blake2s 常数的字节搜索也全部为空。结论是："只有 MD5 和 SHA-256 存在，那个 160 位输出肯定是自定义的。"**这个结论错了。**

真正的答案：**SHA-1 的前四个 IV 字与 MD5 的 IV 完全相同**，而第五个字（`0xC3D2E1F0`）是由 `mov/movk` 立即数构造的，不是作为常数存储的。字节搜索"SHA-1 IV"会误匹配到 MD5，而唯一能区分两者的那个字，根本不以常数形式存在于内存中。

> **教训 2：常数的缺失不是算法的缺失。** 字节搜索只是*正向*测试。常数可以由立即数构造、被混淆、或运行时才解密。这正是 `natool.crypto_id` 只内置 MD5/SHA-1 共享的前四个字、并把陷阱写进文档、而非假装"完整 SHA-1 IV 搜索"有意义的原因。

## 第四回合 —— 破解自定义 VM

让输出对不上任何标准哈希的那个变换，是一个自定义栈机。它的表头带一个魔数（`0xB3????1B`，已打码）、两个长度字段、一个重定位列表；字节码紧随其后。逆向它分三步：

1. 通过读解释器的分发循环，还原 opcode → 语义的映射（85 条 opcode：压栈、8/16/32/64 位的加载/存储、算术、比较、分支，以及一条通过 `BLR X9` 调用外部函数的 `syscall` opcode）。
2. 为这套 opcode 写一个反汇编器——这就是 `natool.vmdisasm`，opcode 表做成参数，因为每个二进制都不同。
3. 离线重装配语义，并确认输出与设备端逐字节一致。

解释器本身几乎不做数学——每个真实操作都是 `syscall` 进到一个 native 的 SHA-256 压缩函数。VM 的存在是为了隐藏**编排**，并加一层后处理（`out[i] = (sha[i] + t1[i]) ^ t2[i]`），让朴素的黑盒匹配对不上标准 SHA-256。

## 第五回合 —— 受控差分测试（真正的重活）

签名有多个输入。决定性的技术是**一次只改一个变量**并观察输出：

* 同一 canonical 串调用两次 → 字段 `s1` 相同、`s2`/`s4` 不同 → `s1` 是 canonical 串的纯函数；其余字段包含时间戳。
* 翻转哈希输出的一个字节 → 最终值雪崩 → 这是哈希，不是线性组合。
* 故障注入一个已知的哈希输入 → 确认哪个中间量喂给哪个字段。

一个值得记录的小陷阱：一个看起来像"版本号"的输入字段，实际上是**算法选择器**。把它设成另一个值，会把整条流水线切到一条*更简单*的代码路径（固定密钥的纯 SHA-256），这泄露了一个事实——密钥跨会话是恒定的。这个免费的结论，如果走混淆过的主路径，会花长得多的时间才能得到。

## 交付了什么

可复用的部分沉淀成了 `natool`（本仓库）。站点特定的发现——精确的字段布局、根密钥派生链、反调试绕过——**有意不公开**。

## 诚实边界

* **根密钥的来源**（设备密钥从哪来）没有完全解决——只知道它是设备级、且稳定的。
* **canonical 串的构造**只是近似复现；精确的 URL 编码 / 排序规则在 App 的 Java 层。
* **VM 是被理解，而非被自动逆向**——opcode 表只能手工还原。
* 本工作服务于**防御性研究和互操作性**。在生产环境里重签第三方服务的请求，会引出完全超出本仓库范围的合规问题。

## 复盘要点

1. 在 OLLVM 下，静态分析**默认不可靠**；用它来定位，用动态测试来定论。
2. "常数没找到"只是正向测试；永远不是"不存在"的证明。
3. 一次一个变量。受控差分测试几乎总是胜过手读混淆的控制流。
4. "谁调用了它"不等于"它做了什么"。观察数据，而不是调用边。
